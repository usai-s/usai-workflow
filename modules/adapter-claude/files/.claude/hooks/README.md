# .claude/hooks — PreToolUse-хуки Claude Code

## block_wide_fs_search.py — блокировка широкого поиска по диску

Правило одной строкой — в `AGENTS.md` («Жёсткие правила»). Здесь — полное
описание: что и как перехватывается, границы, известные дыры и ложные
срабатывания. Текст справочный, а не нормативный: читать его нужно тем, кто
меняет хук, а не каждому агенту в каждой сессии.

Что на самом деле
  происходит в Git Bash (проверено, не пересказ):
  - `/` — это НЕ `C:\`. `ls -1 /` показывает корень установки Git for
    Windows (`bin cmd dev etc mingw64 proc tmp usr` + файлы инсталлятора);
    сам `C:\` смонтирован отдельно, в `/c` — соседний, а не вложенный путь.
    Значит голый `find /` (без `-L`) физически не доходит ни до
    `node_modules`, ни до кэша NuGet, ни до слоёв Docker, ни до `bin`/`obj`
    проекта — их там просто нет.
  - Часы процессорного времени съедает `/proc` — синтетическая
    файловая система, через которую Git Bash показывает реестр Windows:
    `/proc/registry`, `/proc/registry32`, `/proc/registry64` — настоящие
    (не символические) каталоги колоссального размера; `find
    /proc/registry -maxdepth 2` не успевает пройти даже верхние уровни за
    8 секунд, вернув 6000+ записей.
  - `/proc/cygdrive` — символическая ссылка на `/` (`readlink
    /proc/cygdrive` → `/`). С флагом `-L` (следовать по символическим
    ссылкам) `find -L /` из-за неё не просто медленный, а вообще не
    завершается: заходит в `/proc/cygdrive`, снова видит в нём `/`,
    снова заходит — по кругу.
  - Настоящая опасность для `node_modules`/NuGet/AppData/Docker — не `/`, а
    `/c`, `/c/Users`, `/c/Users/<кто угодно>` и `~` (это то же самое, что
    `/c/Users/<текущий пользователь>`): вот они уже физически ведут к этим
    каталогам, и именно туда указывали все пять процессов-инцидентов.
  Что реально перехватывается: PreToolUse-хук
  `.claude/hooks/block_wide_fs_search.py` (подключён в
  `.claude/settings.json`, матчер `Bash|PowerShell`) разбирает настоящую
  командную строку — составные команды по `&&`/`||`/`;`/`|`/`&`/переносам
  строк, смену каталога через `cd`/`pushd`, кавычки, любой порядок флагов, в
  т.ч. флаги самих обёрток (`sudo -n`, `sudo -u root`, `nice -n 10`,
  `env -i`, `xargs -I{}` — а не только голое имя обёртки без аргументов),
  группировку `(...)`/`{ ...; }`, подстановку команд `$(...)` (рекурсивно,
  той же проверкой: `x=$(find / -name x)`, `echo $(find / -name x)`),
  `bash -c '...'`/`sh -c '...'` (содержимое строки разбирается тем же
  кодом, что и обычная команда) — и блокирует
  `find`/`rg`/`grep -r`/`ls -R`/`du`/`tree`/`Get-ChildItem -Recurse` (и
  алиасы `gci`/`dir`/`ls`), если целевой путь после разрешения — `/`, любой
  бэйр-диск (`/c`, `/d`, ..., `C:\`, `D:\`, ... — форма Git Bash и
  Windows-нативная форма симметричны, любая буква диска, а не только `C:`),
  `/c/Users`/`C:\Users` (тоже для любой буквы диска), один каталог прямо
  под `/c/Users`/`C:\Users` конкретно (НЕ под `/c` или `C:\` произвольно —
  `find /c/Windows`, `find /usr` поддерево не блокируют, это сознательно не
  закрытая часть, см. «Что НЕ перехватывается» ниже) или `~`/домашний
  каталог целиком — в т.ч. если он назван через переменную (`$HOME`,
  `${HOME}`, `$USERPROFILE`, `${USERPROFILE}`, `$env:USERPROFILE`,
  `%USERPROFILE%`): хук не исполняет шелл и не знает истинного значения
  переменной в сессии агента, подставляет своё представление о домашнем
  каталоге текстовым совпадением, не настоящим раскрытием переменных.
  Поддерево глубже (`~/.nuget/packages/...`, `/c/Users/<я>/Workspace/...`)
  не блокируется — это осознанная граница, а не недосмотр: иначе
  легитимный точечный поиск в кэше или в своём же чекауте стал бы
  невозможен; то же верно для `find ... -maxdepth 0`/`-maxdepth 1` (не
  спускается вглубь — дёшево и безопасно независимо от пути, поэтому не
  блокируется вообще, даже по `/`). Проверено оффлайн-таблицей команд
  (`.claude/hooks/tests/`, 94 кейса — 59 BLOCK / 35 ALLOW), без запуска
  настоящего обхода диска: `python .claude/hooks/tests/run_cases.py`. `permissions.deny` в том же
  файле — грубая дублирующая сетка (сравнение по префиксу буквально,
  поэтому не покрывает составные команды и не всё видит), а не основной
  механизм.
  Что НЕ перехватывается механически — остаётся на ответственности агента:
  - вызов из сессии, которая физически стартовала не в каталоге с этим
    `.claude/settings.json`: файл читается только из стартового каталога
    сессии, не ищется вверх по дереву и не перечитывается при `cd` посреди
    сессии — риск именно для фоновых сабагентов, которых оркестратор мог
    запустить не там;
  - у сабагентов (`.claude/agents/*.md`) нет инструмента PowerShell вообще
    (только `Bash`) — PowerShell-ветка хука для них не дыра (пользоваться
    нечем), но живую интерактивную сессию человека с PowerShell она
    защищает только через сам хук, других сеток для неё нет. Сама ветка
    (`tool_name == "PowerShell"`) живьём, в реальной сессии, не
    наблюдалась — проверена только офлайн-таблицей с синтетическим JSON на
    stdin, как и весь остальной хук;
  - обёртки вида `cmd /c "..."` или `powershell -Command "..."`, где
    настоящая команда — строка внутри строки на ДРУГОМ языке разбора (не
    POSIX-шелл); хук её не разворачивает. Это не то же самое, что
    `bash -c '...'`/`sh -c '...'` из инструмента Bash — та форма
    разворачивается (см. выше);
  - переменные шелла и циклы, чьё значение не видно текстуально в самой
    команде: `for d in /; do find $d -name x; done` — хук видит токен
    `$d`, а не то, что цикл присвоит ему `/`; это потребовало бы
    трассировки значений переменных, которую хук не делает;
  - backtick-подстановка (`` `find / -name x` ``) — разбирается только
    `$( ... )`;
  - группировка `(...)` снимается эвристикой на один приклеенный без
    пробела символ с каждого края текста подкоманды — глубоко вложенные
    или несбалансированные скобки вне гарантии;
  - код, который обходит диск не через шелл-команду, а сам по себе
    (Python/`.NET`/сторонняя программа) — хук видит только `tool_input`
    вызовов Bash и PowerShell.
  Известное ложное срабатывание в другую сторону (не дыра, а лишний
  блок): хук не понимает heredoc (`<<'EOF' ... EOF`) — если внутри тела
  heredoc встречается текст вида `find / ...` как ПРИМЕР команды (не как
  реально исполняемый код, а просто записываемые в файл строки), хук всё
  равно его увидит и заблокирует запись файла. Разбор heredoc потребовал
  бы многострочного слежения за границей тела, что выходит за рамки
  «упрощённого разбора» этой задачи.
  Это правило — про Claude Code конкретно (хук и `.claude/settings.json` —
  его механизм). У других инструментов, которые тоже читают этот файл
  (Codex и т.п.), нет ни `.claude/settings.json`, ни хуков, ни `Glob`/`Grep`
  — для них это просто текстовая инструкция без автоматической защиты:
  не начинай поиск с `/`, `/c`, `C:\`, `/c/Users` или домашнего каталога
  целиком, сужай до конкретного поддерева.
  Где искать вместо широкого поиска:
  - кэш пакетов — сразу его подкаталог (`~/.nuget/packages/<пакет>/`,
    `~/.npm/...`), а не кэш целиком;
  - файлы репозитория в Claude Code — инструментами `Glob`/`Grep`;
  - путь неизвестен — сузь до поддерева (`find src -name '*.ext'`): поиск в
    поддереве не запрещён, запрещены только `/`, `/c`, `C:\`, `/c/Users`
    и домашний каталог целиком.
