# Этапы 4–5 — Backend: разработка + QA

**Роли:** backend-developer, qa-engineer (QA — отдельная сессия) · **Модель:** план L-фичи — deep, остальное — standard
**Вход:** `spec.md`, `design.md`, `docs/conventions/backend.md`
**Выход:** код + тесты в ветке фичи, `docs/features/<id>/api-contract.md`, `qa.md` (раздел Backend)

## 4a. План (перед кодом — обязательно)

1. Прочитать конвенции backend и код соседних slice'ов.
2. Написать план: для M — раздел `## Plan` (5–10 строк) в `status.md` фичи;
   для L — отдельный `docs/features/<id>/plan-backend.md`. Содержание:
   затрагиваемые slice'ы, новые endpoint'ы, изменения домена, миграции БД,
   интеграции. Решение уровня «повлияет на все слайсы / выбор технологии /
   отступ от конвенций» — это ADR (`docs/adr/README.md`), не пункт плана;
   в плане — ссылка на него.
3. **Зафиксировать контракт API** в `api-contract.md`: endpoint'ы, DTO
   запрос/ответ, коды ошибок. С этого момента контракт — интерфейс для
   frontend-этапа; менять его можно только с пометкой в `status.md` и строкой
   в Log. Если этап 6 (frontend) уже стартовал — изменение контракта
   эскалируется оркестратору: он решает, какую часть frontend перезапустить.

## 4b. Разработка

- Строго по `docs/conventions/backend.md`.
- Порядок: миграция БД → домен → slice (endpoint/handler) → интеграции.
- Тесты пишутся вместе с кодом, а не после: unit на доменные правила,
  integration на каждый endpoint против реальной БД (инструменты — по
  конвенциям backend).
- Каждый acceptance criterion из `spec.md` должен быть покрыт хотя бы одним
  тестом; в тесте — комментарий-ссылка на story/критерий.
- Коммиты мелкие, по slice'ам. Build и тесты зелёные после каждого коммита.

## 5. QA backend (отдельная сессия, чистый контекст)

QA-агент **не смотрит на реализацию до написания тест-плана** — только
spec + api-contract:

1. Составить раздел **Backend** в `qa.md` фичи по
   `docs/templates/test-plan.md`: матрица критерий → тест, дополнительные
   негативные сценарии, граничные значения, конкурентность, права.
2. Проверить фактическое покрытие: запускать тесты, читать код тестов,
   дописать недостающие. Прогнать миграции на чистой БД.
3. Дефекты — списком в разделе Backend `qa.md` (severity, шаги
   воспроизведения) → возврат backend-developer'у. Цикл до пустого списка
   блокеров.

### Экономия прогонов

QA стоит времени человека, а не только токенов. Проверять надо то, что ещё
не проверено, а не то, что удобно перепроверить:

- **Зелёное не перепроверяется.** Прогон того же набора тестов второй раз
  «на всякий случай» запрещён. Нестабильность ловится повтором только тогда,
  когда есть подозрение на гонку — и тогда это записывается как проверка
  гипотезы, а не как ритуал.
- **Не поднимать окружение руками, если это уже делает тест.** Зелёный
  интеграционный тест на `/health` — достаточное доказательство; ручной
  запуск приложения нужен, только когда проверяется то, чего тест не
  покрывает (например, dashboard оркестратора или связность контейнеров).
- **Мета-проверки гардов — один раз за проект.** Что warnings-as-errors,
  архитектурные правила и хуки действительно срабатывают, проверяется на
  бутстрапе и закрепляется тестом (архитектурные тесты уровня «правило не
  вакуумно»), а не повторяется в каждой задаче.
- **Для каркасных `tech`-задач** (нет бизнес-логики — solution, CI, конфиг)
  полная матрица покрытия не пишется: чек-лист «структура по конвенциям,
  сборка, тесты, запуск» + список дефектов.

## Definition of Done

- [ ] `api-contract.md` зафиксирован
- [ ] Все критерии spec покрыты тестами, тесты зелёные
- [ ] Миграции применяются на чистую БД и повторно (идемпотентность отката проверена)
- [ ] `qa.md`, раздел Backend: блокеров нет
- [ ] `status.md`: `stage: 05-frontend`
