# Этап 3 — UX/UI дизайн → Human Gate 2

**Роль:** ux-designer · **Уровень модели:** standard
**Вход:** `docs/features/<id>/spec.md` (approved), `docs/conventions/frontend.md`
**Выход:** `docs/features/<id>/design.md` + HTML-прототип (опционально)

## Цель

Спроектировать экраны и взаимодействие в терминах компонентов дизайн-системы
проекта (`docs/conventions/frontend.md`) так, чтобы frontend-разработчик
собирал, а не придумывал.

## Процесс

1. Карта экранов: какие экраны/страницы нужны, навигация между ними,
   какая story каким экраном закрывается.
2. Для каждого экрана в `design.md`:
   - layout словами + ASCII/Mermaid-схема расположения блоков;
   - используемые **компоненты дизайн-системы по именам** (например
     DataGrid, Autocomplete, Dialog) — не изобретать кастомные там, где
     есть стандартный;
   - все состояния: loading (skeleton), empty, error, success, права
     (что видит каждая роль);
   - валидации форм и тексты ошибок (на языке артефактов проекта);
   - поведение на mobile/узких экранах, если релевантно.
3. Опционально (для L-фич — обязательно): кликабельный HTML-прототип
   ключевого экрана — один самодостаточный html-файл в
   `docs/features/<id>/prototype/`, чтобы человек посмотрел до разработки.
4. Тексты интерфейса (лейблы, кнопки, пустые состояния) — сразу в design.md,
   это часть дизайна, а не «потом придумаем».

## Правила

- Дизайн-система = стандартные компоненты + тема проекта (конвенции
  frontend). Никаких пиксель-перфект спецификаций — фиксируем структуру,
  компоненты и состояния.
- Переиспользование: перед проектированием посмотреть `design.md` соседних
  фич — одинаковые задачи решаются одинаковыми паттернами.

## Human Gate 2

Оркестратор показывает человеку `design.md` (+ прототип) и summary.
Человек в `status.md`:

```
gate-2: approved | rejected: <что переделать>
```
