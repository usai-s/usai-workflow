# Этап 0 — Legacy-анализ

> Этап существует, только если проект замещает существующую систему и её
> каталог объявлен в `AGENTS.md`. Greenfield-проект без legacy начинает с
> этапа 1.

**Роль:** legacy-analyst · **Уровень модели:** deep
**Вход:** название модуля/функциональности, каталог legacy-системы из `AGENTS.md`
**Выход:** `docs/legacy/<модуль>.md` + ссылка из `docs/features/<id>/status.md`

## Цель

Извлечь из legacy-системы **что** она делает, а не **как**. Результат —
источник требований для этапа 1. Архитектурные решения legacy не переносим.

## Процесс

1. Локализовать модуль: точки входа (контроллеры/страницы/фоновые задания),
   сервисы, слой данных, SQL/схема БД, интеграции и смежные сервисы.
2. Извлечь и зафиксировать:
   - **Бизнес-процессы** — сценарии от действия пользователя до результата;
   - **Бизнес-правила** — валидации, расчёты, статусные машины, ограничения
     (с точной ссылкой на файл:строку в legacy — правила проверяются человеком);
   - **Модель данных** — таблицы, ключевые поля, связи, где живут «странные»
     данные (магические статусы, nullable-костыли);
   - **Интеграции** — внешние системы, форматы, синхронность;
   - **Роли и права** — кто что может.
3. Отдельным разделом — **«Сомнительное»**: мёртвый код, правила, похожие на
   баги, костыли. По каждому — вопрос человеку: переносим ли поведение?
4. Ничего не додумывать. Если правило непонятно — оно попадает в «Сомнительное»
   с вопросом, а не в основной раздел с догадкой.

## Шаблон выхода

`docs/templates/legacy-analysis.md`

## Definition of Done

- [ ] Все точки входа модуля перечислены
- [ ] Каждое бизнес-правило имеет ссылку на код legacy
- [ ] Схема данных модуля описана
- [ ] Раздел «Сомнительное» заполнен (или явно пуст)
- [ ] Открытые вопросы вынесены в конец файла списком для человека
