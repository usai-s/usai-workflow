# Этап 1 — Бизнес-аналитика

**Роль:** business-analyst · **Уровень модели:** standard (спорное — deep)
**Вход:** задача, `docs/legacy/<модуль>.md` (если есть), `docs/backlog.md`
**Выход:** `docs/features/<id>/spec.md` по шаблону `docs/templates/feature-spec.md`

## Цель

Превратить задачу и результаты legacy-анализа в проверяемую спецификацию:
user stories с acceptance criteria, BPMN-процесс, позицию в бэклоге.

## Процесс

1. Прочитать legacy-анализ и текущий `docs/backlog.md`.
2. Написать `spec.md`:
   - контекст и цель (2–4 предложения, зачем это пользователю);
   - user stories в формате «Как <роль>, я хочу <действие>, чтобы <ценность>»;
   - для каждой story — acceptance criteria в Gherkin (Given/When/Then);
   - BPMN основного процесса — Mermaid-диаграмма в самом файле
     (обязательна для L; для M — только если процесс ветвится нетривиально);
   - нефункциональные требования (объёмы, права, аудит) — только реально нужные;
   - out of scope — явный список того, что НЕ делаем;
   - открытые вопросы к человеку.
3. Декомпозировать на задачи для бэклога (каждая ≤ размера M) с зависимостями
   и предложить приоритет. Обновить `docs/backlog.md`. Задачи декомпозиции
   пишутся с литералом `NNN` (`feat-NNN-<slug>`), без цифр: номер задача
   получает при заведении ветки — иначе полсотни номеров окажутся заняты
   строками в незамерженной ветке, невидимыми для других сессий
   ([../../features/README.md](../../features/README.md), правила нумерации).
4. Расхождения с legacy-поведением помечать явно: `[ИЗМЕНЕНИЕ vs legacy]`.

## Правила

- Каждый acceptance criterion должен быть проверяем автотестом или руками —
  «система должна работать быстро» не критерий, «список ≤ 2с при 10k строк» — критерий.
- Не проектировать реализацию: никаких таблиц БД и endpoint'ов в спеке.
  Контракт API появится на этапе backend.
- Если спека выходит > ~400 строк — фича слишком большая, вернуть оркестратору
  предложение разбить.

## Definition of Done

- [ ] Все stories имеют Gherkin-критерии
- [ ] BPMN-диаграмма отражает и happy path, и отказы (для L; для M — если она есть)
- [ ] «Полнота операций»: у каждой сущности заполнены все клетки — роль либо
      «нет: почему»; операции, отсутствовавшие в legacy (правка, отмена,
      деактивация), решены явно, а не унаследованы молчанием
- [ ] Out of scope заполнен
- [ ] Бэклог обновлён, у задач проставлены зависимости
- [ ] `status.md` фичи обновлён: `stage: 02-requirements-review`
