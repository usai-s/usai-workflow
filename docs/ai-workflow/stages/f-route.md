# F-маршрут — Fast, тривиальная правка

**Исполнитель:** оркестратор в своей же сессии · **Уровень модели:** `fast`
**Вход:** описание правки от человека
**Выход:** правка в ветке задачи + `status.md` (`## Plan`, `## Log`)

Самый короткий маршрут: без спеки, дизайна, плана реализации, отдельной
QA-сессии и отдельного code review. Остаётся один human gate — финальный,
где человек видит полный diff.

## Когда F допустим

Закрытый список. Что не перечислено — это `S`:

- тексты и опечатки в `docs/`, README, комментариях к коду;
- форматирование, применение линтера, порядок импортов;
- переименование локальной переменной или приватного метода **внутри одного
  файла**;
- битая ссылка, опечатка в пути, устаревшее имя файла в документации;
- правка сообщения об ошибке или лога **без изменения условий**, при которых
  оно выдаётся.

Список закрытый намеренно. Пять абстрактных критериев вида «не затрагивает
архитектуру» агент заполнит утвердительно, потому что так короче; список
конкретных случаев — нет.

## Когда F запрещён

- Меняется **наблюдаемое поведение** — любое: ответ API, вывод в UI, порядок
  или условия выполнения. Это минимум `S`.
- `bugfix` и `hotfix` — никогда не F: у бага есть тест, падавший до фикса,
  а значит есть и изменение поведения.
- Затронуты auth, права, секреты, контракт API, схема данных, миграции, CI,
  инфраструктура, интеграции, архитектура или бизнес-правила из legacy.
- Правка в нескольких файлах, связанных логикой (а не одинаковой опечаткой).
- **Сомневаешься — значит `S`.** Сомнение здесь и есть признак нетривиальности.

## Процесс

1. **Старт (оркестратор).** Как обычно и без сокращений: резерв номера в
   `docs/backlog.md`, папка `docs/features/<id>/` со `status.md`, ветка и
   отдельный worktree по правилам [../../features/README.md](../../features/README.md)
   и [../../conventions/git.md](../../conventions/git.md). Тривиальность
   правки не повод коммитить в `main` или работать в чужом каталоге.
2. **До первой правки** в `status.md`: `size: F`, `gates: gate-3`, а в
   `## Plan` — одна строка
   вида «что правим · к какому пункту списка допуска относится · чем
   проверяем». Проверка по умолчанию — `scripts/verify.sh`: он запускает
   проверки, объявленные проектом в `scripts/verify.config.sh`. «Проверить
   глазами» проверкой не считается — у неё нет кода возврата.
3. **Правка.** Оркестратор делает её сам, в этой же сессии. Отдельный
   dev-субагент не нужен: работа механическая.
4. **Проверка.** Прогнать `scripts/verify.sh` (или команду из плана, если
   она у́же), записать в `## Log` саму команду и код возврата. Красный
   результат — стоп, см. «Эскалация».
5. **Финальный human gate.** Оркестратор готовит пакет для человека по
   [06-review-complete.md](06-review-complete.md) — что изменено и результат
   проверки — и останавливается. Полный diff человек смотрит целиком: на F
   это и есть ревью. Строку `gate-3` пишет только он.

Отдельные `spec.md`, `design.md`, `plan-*.md`, `qa.md` для F не создаются.

## Эскалация в S

Если по ходу выяснилось, что правка выходит за список допуска, diff вырос за
пределы задуманного или проверка покраснела — задача **становится `S`**:
в `status.md` меняется `size: F` → `size: S`, в `## Log` пишется причина, и
дальше работа идёт по [s-route.md](s-route.md) с полноценными QA и code review.

Возврат в F после эскалации запрещён. Цена ошибки классификации должна быть
асимметричной: подняться легко, спуститься нельзя — иначе F станет способом
обойти процесс.

## Definition of Done

- [ ] `size: F` и однострочный `## Plan` записаны **до** первой правки
- [ ] Правка укладывается в закрытый список допуска
- [ ] `scripts/verify.sh` зелёный; команда и код возврата записаны в `## Log`
- [ ] Наблюдаемое поведение не изменилось
- [ ] Запрос на merge отправлен человеку, `gate-3` остаётся за ним
