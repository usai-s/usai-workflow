# Routing: маршрут задачи и выбор модели

## 1. Workflow routing — какой маршрут проходит задача

Оркестратор классифицирует каждую входящую задачу по двум осям.

### Тип задачи

| Тип | Префикс id | Примеры | Маршрут |
|-----|-----------|---------|---------|
| `bugfix` | `bug` | падает запрос, неверный расчёт | Dev → QA → Review → PR (этапы 0–3 пропускаются) |
| `hotfix` | `hot` | прод лежит, критичный дефект у пользователей | S-маршрут от `main`, вне очереди; гейт-3 и зелёный CI обязательны |
| `tech` | `tech` | рефакторинг, апгрейд зависимости, CI | Dev → QA → Review → PR |
| `feature` | `feat` | новая пользовательская функциональность | полный маршрут (или с этапа 1, если legacy-анализ модуля уже есть) |
| `module` | `mod` | целый модуль (из legacy-системы или новый) | полный маршрут с этапа 0, декомпозиция на features |
| `docs/analysis` | `doc` | только исследование или документ | этапы 0–2, без разработки |

Формат id и правила нумерации — [docs/features/README.md](../features/README.md).
`hotfix` отличается от `bugfix` только срочностью и точкой ветвления: он всегда
S, всегда от свежего `main` и не ждёт очереди в backlog — но проходит те же
тест, ревью и gate-3. «Срочно» не отменяет ни одного из них.

### Размер

| Размер | Критерий | Что меняется |
|--------|----------|--------------|
| `F` | тривиальная правка без изменения поведения: опечатка, комментарий, форматирование, битая ссылка | Ни спеки, ни дизайна, ни плана. Нет отдельных QA- и review-сессий: проверка — одна детерминированная команда, ревью — человек на финальном гейте. Закрытый список допуска: [stages/f-route.md](stages/f-route.md) |
| `S` | ≤ ~2 ч работы, 1–5 файлов, один слой | Без спеки и дизайна. План — 3–5 строк в `status.md`. Один human gate — ревью перед PR. Процесс: [stages/s-route.md](stages/s-route.md) |
| `M` | одна фича в существующем slice | `spec.md` в сокращённой форме (stories + критерии, BPMN опционален), дизайн только если есть новые экраны |
| `L` | **заведение** нового slice/модуля либо любой из «Порогов `L`» ниже | Полный пайплайн, все 3 гейта, обязательный legacy-анализ |

Занижение размера запрещено: сомневаешься между M и L — бери L.

### Подтверждение маршрута

Классификацию **всегда подтверждает человек** — до резерва номера, ветки и
первой правки. Не «при сомнении»: агент, ошибшийся в размере, сомнения как
раз и не испытывает, иначе взял бы больший режим. Дешевле спросить один раз,
чем обнаружить пропущенные гейты на этапе ревью.

Оркестратор показывает блок и останавливается:

```
МАРШРУТ · <суть задачи>

Тип:     <feature | bugfix | hotfix | tech | module | docs> (префикс <...>)
Размер:  <F | S | M | L> — <одна строка: почему именно этот — по чек-листу>
Маршрут: <этапы через стрелки — вычеркните лишние>
Гейты:   <применимые; неприменимые с причиной, почему у них нет предмета>
Артефакты: <spec.md / design.md / plan / только status.md>

Подтвердить или назвать другой размер.
```

Ответ человека записывается строкой в `## Log` задачи. Молчание
подтверждением не считается.

Смена классификации по ходу работы (эскалация `F` → `S`, `M` → `L`) — это
новый маршрут, а значит новое подтверждение. Понижать размер после
подтверждения нельзя вообще: см. [stages/f-route.md](stages/f-route.md).

Для `F` правило занижения строже остальных: **любое изменение наблюдаемого
поведения поднимает задачу минимум до `S`**, а `bugfix` и `hotfix` не бывают
`F` никогда — у бага есть тест, падавший до фикса, то есть изменение
поведения по определению. Выяснилось по ходу, что правка сложнее ожидаемого,
— задача становится `S` и обратно в `F` не возвращается.

**Уточнение для greenfield-этапа проекта.** Дорого стоит именно *открытие* нового
slice: границы модуля, модель данных, контракт API, первые миграции. Поэтому `L` —
это **первая** задача в slice, та, что его заводит. Последующие задачи внутри уже
заведённого slice — `M`, даже если они добавляют экраны и миграции: каркас уже
задан и проверен на трёх гейтах.

Без этого уточнения на старте проекта, где существующих slice'ов нет по
определению, размер `L` получала бы каждая задача, а число human gates росло бы
линейно с бэклогом — гейты обесцениваются и превращаются в формальность.

Правило не отменяет запрет на занижение: если задача внутри существующего slice
**ломающим образом** меняет его границы, модель данных или контракт API — это
снова `L`. Добавление нового (таблицы, колонки, поля DTO, endpoint'а) — не
ломающее изменение; переименование, удаление, смена типа или семантики
существующего — ломающее.

### Чек-лист определения размера

Заполняется агентом **до** блока `МАРШРУТ` и показывается вместе с ним.
На блоки 0–2 агент отвечает сам из кода и описания задачи — кроме
наполненности таблиц (вопрос 3.2), которую до ответа на порог о миграции
нужно спросить у человека. Остальные вопросы блока 3 задаются человеку —
только те, что относятся к задаче.

**Блок 0 — тривиальность.**

| # | Вопрос | Следствие |
|---|--------|-----------|
| 0.1 | Меняется ли наблюдаемое поведение системы — хоть для одного пользователя, теста или интеграции? | «да» → блок 1. «нет» → `F`, только если правка входит в закрытый список допуска [stages/f-route.md](stages/f-route.md) **и** блок 1 чист (задача без изменения поведения, но с ADR-порогом — всё равно `L`); иначе `S` |

**Блок 1 — признаки `L`.** Пройди список «[Пороги, при которых размер обязан
быть `L`](#пороги-при-которых-размер-обязан-быть-l)» ниже — он и есть блок 1,
по вопросу на порог. Любое «да» = `L`, остальные вопросы можно не задавать.
Единственный источник формулировок — сам список порогов: здесь он не
дублируется, чтобы не разъезжаться (дубль этого списка в первых редакциях
разошёлся с оригиналом дважды за день). Для порога о миграции наполненность таблиц
уточняется вопросом 3.2 — задай его человеку до ответа.

**Блок 2 — граница `S`/`M`** (если блок 1 чист).

| # | Вопрос | Следствие |
|---|--------|-----------|
| 2.1 | Работа укладывается в ~2 ч **и** 1–5 файлов **и** один слой? | все три «да» → `S`; любое «нет» → не `S` |
| 2.2 | Миграция обратима по данным (порог о миграции уже дал «нет»)? Аддитивная (таблица, колонка, индекс, расширение типа) или обратимое изменение схемы (удаление индекса, constraint) | справочный вопрос: фиксирует характер миграции в блоке `МАРШРУТ`; на размер уже не влияет |
| 2.3 | Затрагивается больше одного слоя (домен + API + экран), но всё внутри своего модуля? | «да» → `M` |

**Блок 3 — вопросы человеку** (того, чего в коде нет).

| # | Вопрос | Зачем |
|---|--------|-------|
| 3.1 | Есть ли у задачи нормативное основание (Правила, регламент, протокол с внешней стороной), которое нужно сверить? | Юридическая цена ошибки может поднять до `L` |
| 3.2 | Содержат ли таблицы, которые трогает миграция, данные (прод или стенды с важными данными)? | Вход для порога о миграции: необратимое преобразование по наполненной таблице = `L` |
| 3.3 | Ожидается ли от задачи больше, чем написано в её строке? | Главный источник эскалаций «`M` выросла в `L`» |

**Правило вывода:**

```
F — блок 0 дал «нет» + допуск f-route + ни один порог L не сработал
L — сработал хотя бы один порог из списка «Пороги L»
S — пороги чисты и все три условия 2.1 выполнены
M — всё остальное
```

Блок 3 размер автоматически не меняет: 3.2 — вход для порога о миграции, а ответы 3.1 и
3.3 прикладываются к блоку `МАРШРУТ` — поднять по ним размер решает человек
при подтверждении.

Сомнение между двумя размерами — всегда больший. Ответы чек-листа входят в
блок `МАРШРУТ` строкой «Размер: … — почему» и фиксируются в `## Log` задачи
вместе с подтверждением человека.

### Пороги, при которых размер обязан быть `L`

**Тип задачи не ограничивает её размер.** Таблица типов говорит, какие этапы
проходятся, а не насколько задача велика: `tech` бывает и `S`, и `L`. Пока
это не было записано, префикс `tech` работал как негласный пропуск на
короткий маршрут.

Задача — `L`, даже если по описанию выглядит технической мелочью, когда
выполнено хотя бы одно:

- миграция БД **необратима по данным** — откат сам по себе данные не вернёт
  (перенос между таблицами, преобразование с усечением, удаление, разбиение
  таблицы) — **и затрагиваемые таблицы уже содержат данные** (наполненность
  подтверждает человек, вопрос 3.2 чек-листа). Добавление таблиц, колонок и
  индексов **своего** модуля порогом не считается (согласовано с greenfield
  выше); добавление в чужой модуль — изменение его границ, порог ниже;
- в решении появляется **новый проект/пакет** (единица сборки);
- принимается **ADR** — то есть решение, которое переживёт задачу;
- заводится новый slice или модуль (см. уточнение для greenfield выше);
- **ломающим образом** меняются границы существующего slice, модель данных
  или контракт API. Ломающее = переименование, удаление, смена типа или
  семантики существующего; добавление нового (таблица, колонка, поле DTO,
  endpoint) — не ломающее;
- меняется **обмен с внешним контрагентом**, чьё поведение мы не
  контролируем (платёжный шлюз, госсервис, партнёрское API): ошибку там
  нельзя исправить одним деплоем;
- меняются **правила аутентификации/авторизации или обращение с секретами**:
  цена незаметной ошибки — открытый endpoint или утечка.

**`hotfix` и пороги.** Хотфикс всегда идёт S-маршрутом (см. таблицу типов) —
даже если инцидент попадает в пороги 1.5/1.6: тушить прод полным пайплайном
нельзя. Компенсация: gate-3 и зелёный CI обязательны, а до merge хотфикса в
очередь заводится tech-задача полного маршрута на доработку того же места.

**Эскалация по объёму.** Если по ходу работы диффа стало вдвое больше
ожидаемого при подтверждении маршрута — остановись, переклассифицируй и
запроси подтверждение заново. Понижать размер нельзя ни в каком случае.

> Пороги записаны по итогам реального инцидента: `tech`-задача с `size: M`
> выросла до 32 файлов и 2418 строк, завела новый тестовый проект, первые
> миграции и ADR — и прошла мимо первых двух гейтов, потому что короткий
> маршрут полагался на префикс `tech`, а не на масштаб. Формулировка порога
> о миграциях тоже выстрадана: «добавляются или меняются миграции» объявляла
> `L` любую миграцию и противоречила greenfield-уточнению; порогом стала
> необратимость по данным.

### Правила пропуска этапов

- Этап 0 пропускается, если `docs/legacy/<модуль>.md` уже существует и покрывает задачу.
- Этап 3 (дизайн) пропускается, если нет изменений UI.
- Этапы 6–7 (frontend) пропускаются для чисто backend-задач, и наоборот.
- Human gates не пропускаются никогда. Но гейт может быть **неприменим**:
  пропущен этап 3 — у `gate-2` нет предмета, и он не появляется в `status.md`
  вовсе. Применимые гейты перечислены в техническом поле `gates:`; их
  значение по-прежнему ставит только человек
  ([../features/README.md](../features/README.md)).

### Сокращения маршрута для `M`

Календарное время задачи съедают не этапы, а ожидание человека: агентские
шаги идут минутами, гейт — часами или днями. Поэтому у `M` два сокращения:

- **`gate-1` и `gate-2` показываются одним пакетом** после этапа 3. Спека и
  дизайн у `M` небольшие, и держать между ними отдельную остановку — значит
  платить вторым ожиданием за просмотр пары экранов. У `L` гейты остаются
  раздельными: там дизайн опирается на утверждённую спеку настолько, что
  делать его до approve — риск переделки.
- **Один проход QA вместо двух.** У `M` этапы 5 и 7 сливаются в один QA после
  frontend: критерии приёмки общие, а два тест-плана на одну небольшую фичу —
  дублирование. У `L` два прохода остаются.

Оба сокращения — про логистику, а не про строгость: code review, тесты вместе
с кодом и финальный гейт не трогаются ни при каком размере.

## 2. Model routing — какая модель на каком этапе

Принцип: **дорогая/умная модель — там, где ошибка дорого стоит или нужно
мышление; быстрая — там, где работа механическая.** Названия моделей меняются,
поэтому фиксируем уровни:

Vendor-адаптеры резолвят эти уровни независимо: Claude Code — через алиасы в
`.claude/agents/*.md`, Codex — через `model` и `model_reasoning_effort` в
`.codex/agents/*.toml`. Таблица уровней описывает назначение класса, а не
вечное имя конкретной модели.

| Уровень | Claude | Codex/OpenAI | Использование |
|---------|--------|--------------|---------------|
| `deep` | Opus / старшая модель, extended thinking | `gpt-5.6`, reasoning high | Архитектурные решения, legacy-анализ, бизнес-аналитика, ревью требований, QA `L`-задач, code review, разбор сложных багов |
| `standard` | Sonnet | `gpt-5.6-terra`, reasoning medium | Дизайн, написание кода и тестов, QA `S`/`M`-задач |
| `fast` | Haiku | `gpt-5.6-luna`, reasoning low | Механика: переименования, генерация boilerplate по образцу, форматирование, черновые summary |

**Единственный источник маппинга «роль → уровень» — таблица ниже.** Vendor
profiles обязаны ей соответствовать; `scripts/validate-ai-workflow.py`
детерминированно сверяет Claude и Codex конфигурации, поэтому незамеченный
дрейф между двумя копиями больше не проходит `verify`.

| Роль | Уровень по умолчанию | Override |
|------|----------------------|----------|
| legacy-analyst | `deep` | — |
| business-analyst | `deep` | — |
| requirements-reviewer | `deep` | — |
| ux-designer | `standard` | — |
| backend-developer | `standard` | план `L` → `deep` |
| frontend-developer | `standard` | — |
| qa-engineer | `standard` | QA `L` → `deep` |
| code-reviewer | `deep` | — |

Принципы, по которым расставлены уровни:

- deep — этапы, формирующие и проверяющие требования (0–2), ревью (8) и
  план/QA `L`-задач: ошибка там либо невосстановима, либо дорога;
- standard — исполнение по готовым артефактам (дизайн, код, QA `S`/`M`);
- fast — механика (changelog, PR-текст).

### Стоимость прогона — тоже критерий

Уровень модели — не единственный источник цены. На бутстрапе одного из проектов backend-QA занял 11 минут и 67 вызовов
инструментов, и бо́льшая часть — повторные прогоны сборки и тестов и подъём
тестового окружения, а не мышление. Правила экономии — в разделах QA этапов 4–7 и в
[stages/s-route.md](stages/s-route.md); главное: **зелёное не
перепроверяется повторным прогоном того же самого**.

## 3. Параллелизм

- Независимые фичи ведутся в отдельных ветках/worktree — по одной сессии на фичу.
- Внутри фичи: backend QA (этап 5) может идти параллельно со стартом frontend
  (этап 6), т.к. frontend работает против `api-contract.md` и моков.
- Ревьюеры (этапы 2, 8) — всегда **отдельная сессия/субагент с чистым
  контекстом**, никогда не тот же контекст, что писал артефакт: ревьюер,
  видевший ход мыслей автора, наследует его слепые пятна.
