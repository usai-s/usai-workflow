# docs/features/ — рабочие папки фич

Каждая задача = папка `docs/features/<id>/`. Это состояние пайплайна задачи;
любой агент (Claude Code, Codex, человек) продолжает работу, прочитав эту папку.

## Идентификатор задачи

Формат: **`<префикс>-<NNN>-<slug>`** — например `feat-001-user-profile-form`,
`bug-014-price-rounding`, `hot-002-report-pdf-500`.

| Часть | Правило |
|-------|---------|
| `<префикс>` | тип задачи, см. таблицу в [routing.md](../ai-workflow/routing.md): `feat`, `bug`, `hot`, `tech`, `mod`, `doc` |
| `<NNN>` | порядковый номер, 3 цифры с ведущими нулями, счётчик **свой для каждого префикса** (`feat-001` и `bug-001` существуют одновременно). Исключение: у предложенной, но не начатой задачи вместо цифр стоит литерал `NNN` — см. правила нумерации ниже |
| `<slug>` | kebab-case, латиница, 2–4 слова по сути задачи |

Правила нумерации:

- **Номер считается по всем веткам сразу, а не по одному файлу.** Следующий
  номер = максимальный номер этого префикса + 1, где максимум берётся по
  **объединению** трёх источников. Они перечислены по убыванию надёжности, но
  приоритета между ними нет — брать надо максимум по всем трём, а не значение
  из первого, где нашлось:
  1. **имена веток** — `git branch --all`, приведённые к id (`tech/005` →
     `tech-005`). Самый надёжный: номер занятой, но ещё не смерженной задачи
     виден только здесь. Перед расчётом — `git fetch --prune`, иначе
     remote-tracking ветки показывают состояние последнего fetch;
  2. каталоги `docs/features/<id>/` — во всех ветках, не только в текущей:
     `git for-each-ref --format='%(refname)' refs/heads refs/remotes | xargs -I{} git ls-tree --name-only {}:docs/features`;
  3. `docs/backlog.md` — тоже во всех ветках, включая раздел `Done`:
     `git for-each-ref --format='%(refname)' refs/heads refs/remotes | xargs -I{} git show {}:docs/backlog.md`.

  Обход ограничен `refs/heads refs/remotes` намеренно — иначе в выборку попадает
  `refs/stash`.

  Номер выдаёт `scripts/new-task.sh` (он обходит все три источника по всем
  веткам); посмотреть занятые — `scripts/backlog.sh --ids`. Ручной расчёт по
  трём источникам — запасной путь.
- **Почему не «источник истины — backlog.md».** Ровно так правило и было
  записано раньше, и оно сломалось: параллельные сессии в разных worktree брали
  максимум по бэклогу **своей** ветки, ветки долго не мержились, и номера
  `tech-005` и `tech-006` достались двум разным задачам каждый. Бэклог
  становится общим только после merge — до merge это один из источников, а
  не главный.
- **Резервирует номер ветка, а не строка в бэклоге.** Порядок заведения задачи:
  сначала ветка `<префикс>/<NNN>-<slug>`, потом строка в `docs/backlog.md` и
  `docs/features/<id>/status.md`. Строку в бэклоге незамерженной ветки видит
  только та сессия, которая её написала; имя ветки — все и сразу.
- **Предложенная, но не начатая задача номер не занимает.** Когда по ходу
  работы рождается идея следующей задачи, пиши в бэклоге буквально
  `tech-NNN-<slug>` — без цифр. Номер присваивается в момент, когда задачу
  берут в работу и заводят ветку. Иначе номер «висит» строкой в незамерженной
  ветке, невидимый другим.
- **Если номер всё же выдан дважды** — окно между расчётом максимума и
  созданием ветки не нулевое — переименовывается та задача, чей id ещё не утёк
  в смерженные артефакты. Посчитай ссылки по всем веткам до того, как выбирать:
  `git for-each-ref --format='%(refname)' | xargs -I{} git grep -c <id> {}`.
  Переименование оставляет хвост битых ссылок; их правка входит в ту же задачу,
  а не откладывается — иначе старый id продолжает резолвиться, но уже в чужую
  задачу.
- Отменённая задача номер не освобождает: её папка `docs/features/<id>/`
  остаётся с пометкой в `status.md`.

- **Номера не переиспользуются.** Отменённая задача остаётся строкой в backlog
  со статусом `cancelled`, её номер не достаётся другой задаче. Если задачу
  отменили до merge, строка `cancelled` всё равно должна доехать до `main`
  отдельным коммитом: вместе с удалённой веткой номер исчезает из всех трёх
  источников и снова выглядит свободным.
- **Короткая ссылка — `<префикс>-<NNN>`** (`feat-001`): ею ссылаются в
  `deps:`, в заголовке PR, в переписке. Полный `<id>` — в путях и именах веток.
  На ещё не пронумерованную задачу ссылаются слагом
  (`deps:rebase-stacked-branches`), а не `<префикс>-NNN`: литерал `NNN`
  неоднозначен, таких строк в бэклоге может быть много.

## Ветка

`<префикс>/<NNN>-<slug>` — тот же id, где первый дефис заменён на слэш:
`feat/001-user-profile-form`, `bug/014-price-rounding`. Так ветки
группируются по типу (`git branch --list 'bug/*'`), а id остаётся восстановимым.

## Состав папки

| Файл | Появляется на этапе | Назначение |
|------|--------------------|------------|
| `status.md` | старт | машина состояний: текущий этап, лог, вердикты гейтов |
| `spec.md` | 1 | user stories, критерии, BPMN (шаблон: templates/feature-spec.md) |
| `design.md` | 3 | экраны, компоненты, состояния (шаблон: templates/design-spec.md) |
| `plan-backend.md`, `plan-frontend.md` | 4, 6 | планы реализации — только для L; для S/M план пишется разделом `## Plan` в `status.md` |
| `api-contract.md` | 4 | контракт API — интерфейс backend ↔ frontend (обязателен всегда, когда есть API) |
| `qa.md` | 5, 7 | единый тест-план и дефекты, разделы Backend и Frontend (шаблон: templates/test-plan.md) |
| `prototype/` | 3 | HTML-прототипы (опционально) |

Для `F` не создаётся ничего, кроме `status.md`: ни `spec.md`, ни `design.md`,
ни `plan-*.md`, ни `qa.md`. Понадобился любой из них — значит задача не `F`
(см. [f-route.md](../ai-workflow/stages/f-route.md)).

## Формат status.md

```markdown
# <id>

- type: feature | bugfix | hotfix | tech | module | docs
- size: F | S | M | L
- branch: <префикс>/<NNN>-<slug>
- stage: 00-legacy-analysis | 01-business-analysis | 02-requirements-review |
         gate-1 | 03-ux-design | gate-2 | 04-backend | 05-frontend |
         06-review-complete | gate-3 | complete
- legacy: docs/legacy/<модуль>.md | none
- epic: <модуль/волна | platform/<область> | workflow>
- gates: gate-1, gate-2, gate-3   <!-- применимые к маршруту; пишет агент -->

## Gates

<!-- Только гейты из строки `gates:`. Неприменимых здесь нет — их нечего
     «скипать». Значение ставит исключительно человек. -->

gate-1: pending | approved | rejected: <причина>
gate-2: pending | approved | rejected: <причина>
gate-3: pending | approved | rejected: <причина>

## Plan

<!-- для F: одна строка — что правим, пункт списка допуска, команда проверки.
     Для S/M: план реализации 3–10 строк (S — этап старта, M — этапы 4/6).
     Для L вместо этого раздела — файлы plan-backend.md / plan-frontend.md. -->

## Log

- 2026-08-21 [business-analyst] spec.md готов, 2 открытых вопроса
- ...

## Notes

Изменения api-contract, эскалации, решения по ходу работы.
```

Правила:

- Строку `stage:` меняет тот, кто завершил этап; лог append-only.
- **Какие гейты применимы** — следствие маршрута, это техническое поле
  `gates:`, и его заполняет агент. **Значение гейта** — решение человека, и
  ничего кроме `pending` агент туда не пишет никогда. Раньше эти два разных
  факта жили в одной строке (`gate-1: skipped (S-route)`), из-за чего правило
  «gate-строки пишет только человек» противоречило инструкции S-маршрута.
- Строки `gate-N` выражают решение человека и только его. Человек либо правит
  строку сам, либо даёт явный approve/reject в чате — тогда оркестратор
  записывает `approved (подтверждено человеком в чате, <дата>)`. Выводить
  approve из молчания, из вердикта AI-ревьюера или «по контексту» запрещено.
- Содержательное изменение `spec.md` после `gate-1: approved` (или `design.md`
  после `gate-2: approved`) сбрасывает соответствующий гейт в `pending` со
  строкой в Log — фича возвращается на повторный approve. Опечатки и
  форматирование гейт не сбрасывают.
