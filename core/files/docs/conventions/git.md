# Git-конвенции: ветки, коммиты, PR, релизы

Модель — **trunk-based**: одна долгоживущая ветка `main` и короткоживущие
ветки задач. Никаких `develop` и `release/*`: ветка задачи живёт дни, не
недели, и мержится в `main` целиком после человеческого approve.

## Ветки

| | |
|---|---|
| Долгоживущая | `main` — всегда зелёная, всегда пригодна к выкатке |
| Ветка задачи | `<префикс>/<NNN>-<slug>` — `feat/001-user-profile-form`, `bug/014-price-rounding` |

Имя ветки = id задачи, где первый дефис заменён на слэш. Формат id, префиксы
и правила нумерации — [../features/README.md](../features/README.md).

- Ветка создаётся **от свежего `main`** (`git fetch && git switch -c … origin/main`).
- Одна задача — одна ветка. Не складывать в неё попутные правки: найденный
  долг идёт строкой в [../backlog.md](../backlog.md), а не в текущий diff.
  Такая строка пишется с литералом `NNN` вместо цифр (`tech-NNN-<slug>`) —
  номер задача получает, когда её берут в работу и заводят ветку
  ([../features/README.md](../features/README.md)).
- Прямые коммиты в `main` запрещены — только merge PR.
- После merge ветка удаляется (на GitHub — автоудаление, локально
  `git branch -d`). История задачи остаётся в `docs/features/<id>/`.
- Независимые задачи ведутся в отдельных worktree, чтобы параллельные сессии
  агентов не толкались в одном рабочем каталоге.

## Коммиты внутри ветки

- Язык — английский (правило из `AGENTS.md`); артефакты в `docs/` — русские.
- Заголовок — императив, ≤ 72 символов, без точки: `Add profile update handler`.
- Тело (по необходимости) — **почему**, а не что: diff показывает что.
- Гранулярность свободная: ветка схлопывается при merge, поэтому дробные
  «wip»-коммиты допустимы. Но каждый коммит должен собираться — иначе
  `git bisect` бесполезен.
- Никогда не коммитить секреты, `.env`, дампы БД, содержимое каталога legacy-системы.

## Pull Request

1. Открывается **только после `gate-3: approved`** в `status.md`.
2. Перед открытием: rebase на `main`, полный прогон тестов и линтеров. Если
   `main` принёс свои миграции БД — миграции задачи перегенерируются поверх
   свежего `main`.
3. Заголовок: `feat|fix|chore(<scope>): <суть> (<короткий id>)` —
   `feat(profile): add user profile form (feat-001)` — заголовок,
   как и коммиты, английский (правило AGENTS.md; `commit-msg`-хук отклонит
   кириллицу в заголовке squash-коммита).
4. Описание: ссылка на `docs/features/<id>/`, summary изменений, чек-лист
   гейтов, инструкция ручной проверки.
5. **Красный CI — стоп.** PR не открывается и не мержится с падающими
   тестами или линтерами.

## Merge в main

**Способ — squash merge.** Одна задача = один коммит в `main`; история
`main` читается как список выполненных задач, а не как поток «wip»-шума.
Rebase-merge и merge-commit не используются.

Заголовок squash-коммита = заголовок PR (с коротким id) — по нему
восстанавливается связь коммит → задача → `docs/features/<id>/`:

```
git log --oneline --grep 'feat-001'
```

После merge: `status.md` задачи уже содержит `stage: complete` (ставится в
ветке перед merge); backlog при завершении не трогается — новые найденные
задачи добавляются в него строками с литералом `NNN`.

## Локальные проверки (git-хуки)

Хуки лежат в `.githooks/` — обычные `sh`-скрипты, **без npm-зависимостей**
(husky и подобные не используются: лишняя зависимость в цепочке поставки и
не работает у тех, кто не запускает `npm ci`).

Включаются один раз командой:

```
git config core.hooksPath .githooks
```

Стоит автоматизировать её в сборке проекта (например, target в
`Directory.Build.props` или postinstall-скрипт) — тогда хуки включаются сами
на первой сборке.

| Хук | Что проверяет |
|-----|---------------|
| `pre-commit` | коммит не в `main`; имя ветки по формату; секреты и дампы в индексе; маркеры конфликта |
| `commit-msg` | заголовок ≤ 72 символов, английский, без точки в конце |
| `pre-push` | `scripts/verify.sh` — проверки по классу изменённых файлов; тот же вход указан в Definition of Done этапов, поэтому хук и DoD не расходятся |

> Хуки — **обратная связь, а не барьер**: `git commit --no-verify` снимает
> их целиком. Всё, что критично, должно дублироваться в CI.

## Архитектурные тесты (рекомендация)

Границы слоёв и слайсов стоит проверять кодом, а не глазами ревьюера:
тестами, которые читают структуру проекта (направление зависимостей, чистота
домена, изоляция слайсов) и падают в обычном прогоне тестов. Обязательный
элемент такого набора — проверка «правила не вакуумны»: тест, который
убеждается, что проверки всё ещё что-то читают, иначе зелёный статус
обесценивается молча.

Меняется архитектура — сначала правится ADR и конвенция, потом правило в
тестах, и только потом код. Обратный порядок означает, что конвенция
переписывается задним числом под уже сделанное.

## Параллельная работа

Над проектом одновременно работают несколько сессий агентов. Git не изолирует
их внутри одного рабочего каталога: блокировок нет, побеждает тот, кто записал
последним. Общими оказываются не только файлы, но и `obj/`, `bin/`,
`node_modules/` — два одновременных `dotnet build` в одном каталоге портят друг
другу промежуточные файлы, и ошибка выглядит как что угодно, кроме гонки.

### По умолчанию — worktree на поток

Одна сессия = один worktree = одна ветка:

```
scripts/new-task.sh feat user-profile-form "Форма профиля пользователя" M
```

Скрипт берёт следующий свободный номер, заводит ветку от `main`, создаёт
worktree `../<репозиторий>-worktrees/<id>/` и папку фичи со `status.md`.
Ничего не коммитит — созданное остаётся на проверку. Вручную то же самое:

```
git worktree add ../myrepo-worktrees/feat-001-user-profile-form -b feat/001-user-profile-form main
git worktree remove ../myrepo-worktrees/feat-001-user-profile-form
```

Git не даст двум worktree встать на одну ветку — это не ограничение, а нужное
поведение. Хуки при этом работают: `core.hooksPath` хранится в общем конфиге.

Что нужно знать про worktree:

- **Untracked-файлы не переезжают.** `.env`, локальные секреты и конфиги в
  новом каталоге отсутствуют — их создают заново. Это самая частая причина
  «после перехода всё сломалось».
- `obj/`, `bin/`, `node_modules/` — свои в каждом каталоге: первая сборка и
  `npm ci` будут полными.
- Основной каталог репозитория держится на `main` и служит хабом: оттуда
  создают worktree и туда мержат. Агенты в нём не работают — иначе соседняя
  сессия переключит ветку под ними.

### Если потоки всё же в одной фиче

Штатный случай из [../ai-workflow/routing.md](../ai-workflow/routing.md):
backend-QA идёт параллельно со стартом frontend. Тогда потоки делятся по
**зонам владения** — непересекающимся путям:

| Зона | Кто пишет |
|------|-----------|
| backend-каталоги (`src/`, `tests/` и т.п.) | backend-поток |
| `frontend/` | frontend-поток |
| корневые файлы решения (`*.sln`, `Directory.*.props`, lock-файлы), `docs/features/<id>/status.md`, `docs/backlog.md` | **только оркестратор** |

Общие файлы из последней строки — источник почти всех конфликтов.
Агент, которому нужно их изменить, просит оркестратора, а не правит сам.

Для `L`-задач вместо зон надёжнее подветки: `feat/001-…-backend` и
`feat/001-…-frontend` в своих worktree, обе мержатся в ветку фичи. Цена —
два merge; выигрыш — полная изоляция. Frontend при этом работает против
`api-contract.md`, а не против кода backend.

### Правила записи

- **Никогда `git add -A` и `git add .`** — только явные пути. Одно это
  правило снимает половину инцидентов: `-A` подхватывает файлы, созданные
  соседней сессией секунду назад, и они уезжают в чужой коммит.
- `git status` — непосредственно перед `git add`, а не «я смотрел пять минут
  назад». Пять минут назад — это прошлое состояние репозитория.
- **Read-modify-write вместо перезаписи целиком.** Файл перечитывается прямо
  перед записью; содержимое, прочитанное в начале задачи, уже неактуально.
  Это относится и к «маленькой правке» — перезапись целого файла из памяти
  затирает чужие строки молча, без конфликта.
- Раздел `Log` в `status.md` — только дописывание в конец. Append-only
  конфликтует несравнимо реже, чем правка середины.
- Не собирать и не ставить зависимости одновременно в одном каталоге.

## Защита main

Правило «не коммитить в `main`» должно держаться настройкой, а не
дисциплиной агента. На GitHub для `main` включаются:

- запрет прямого push и force-push;
- PR обязателен, минимум одно approve;
- обязательный зелёный статус CI (`ci.yml`);
- автоудаление веток после merge.

> **Статус: не настроено.** Пока правило держится только на инструкциях
> агентам — считать это временным состоянием, а не нормой.

## Релизы и версии

- Версионирование — `MAJOR.MINOR.PATCH` (SemVer), тег `vX.Y.Z` на коммите
  в `main`.
- Тег ставится вручную по решению человека; выкатка в прод — только с тега,
  не с произвольного коммита `main`.
- Теги не переписываются: тег — точка, на которую могут ссылаться внешние
  процессы (приёмка, аудит, changelog).

> **Статус: политика зафиксирована, процесс выкатки не описан** — появится
> вместе с окружениями (stage/prod) и CD-пайплайном.

## Hotfix

`hotfix` отличается от `bugfix` только срочностью и точкой ветвления:
ветка от свежего `main`, задача идёт вне очереди backlog. Маршрут — S
([../ai-workflow/stages/s-route.md](../ai-workflow/stages/s-route.md)), но
тест, воспроизводящий дефект, code review и `gate-3` остаются обязательными.
«Срочно» не отменяет ни одного из них.

Если хотфикс попадает в «Пороги `L`» из
[../ai-workflow/routing.md](../ai-workflow/routing.md) (необратимая миграция,
обмен с внешним контрагентом, auth/секреты) — он всё равно идёт S-маршрутом,
но **до его merge** в очередь backlog заводится tech-задача полного маршрута
на доработку того же места. Хотфикс без такой строки в очереди не мержится.
