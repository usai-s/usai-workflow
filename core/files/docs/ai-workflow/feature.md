# Feature orchestration — единый контракт

Этот файл — общий источник поведения оркестратора для Claude Code и Codex.
Vendor-адаптеры только подключают этот контракт к своим skill/command и
механизму субагентов; правила маршрута, гейтов и передачи состояния здесь не
дублируются.

## Старт задачи

1. Прочитай `docs/ai-workflow/README.md` и `docs/ai-workflow/routing.md`.
2. Если задача уже заведена, прочитай её `docs/features/<id>/status.md` и
   только артефакты, необходимые текущему этапу. Продолжай с `stage:` из файла,
   а не с начала и не из памяти чата.
3. Для новой задачи классифицируй тип, размер `F/S/M/L`, маршрут, гейты и
   артефакты по `routing.md`. Покажи человеку блок `МАРШРУТ` и остановись до
   явного подтверждения. До подтверждения нельзя резервировать номер, создавать
   ветку, worktree, `status.md` или менять файлы.
4. После подтверждения заведи задачу по `docs/features/README.md`. Используй
   `scripts/new-task.sh` в POSIX-shell или `scripts/new-task.ps1` в PowerShell.
   Скрипт резервирует номер веткой, создаёт отдельный worktree и `status.md`.
5. Запиши подтверждённую классификацию и основание размера в `## Log`, затем
   веди всю работу в task worktree. `main` остаётся хабом и не редактируется.

## Маршрут

Размер `F` выполняет сам оркестратор по `stages/f-route.md`, без субагентов,
отдельных QA/review-сессий и дополнительных артефактов.

Для остальных размеров применяй только релевантные роли в таком порядке:

```text
legacy-analyst → business-analyst → requirements-reviewer → gate-1 →
ux-designer → gate-2 → backend-developer → qa-engineer →
frontend-developer → qa-engineer → code-reviewer → gate-3 → merge request
```

Пропуски этапов и сокращения определяет `routing.md`:

- `bugfix`, `hotfix` и `tech` начинают с разработки;
- без UI этап UX и frontend не выполняются, у `gate-2` нет предмета;
- для `M` gate-1 и gate-2 показываются одним пакетом, а QA выполняется одним
  проходом после реализации;
- для `L` план backend выполняется отдельным deep-проходом, реализация —
  standard-проходом; QA также получает уровень deep;
- standing approval снимает только явно разрешённую церемонию и никогда не
  заменяет содержательные human gates.

Каждая роль читает соответствующую инструкцию из
`docs/ai-workflow/stages/*.md` и конвенции проекта. Vendor-адаптер выбирает
конкретный профиль агента и модель по уровням `deep/standard/fast` из
`routing.md`.

## Изоляция контекста и владение файлами

- Каждый этап выполняется свежей сессией или субагентом. QA и review никогда
  не выполняет автор проверяемого артефакта.
- Передавай роли только id задачи, текущий этап, нужные пути и разрешённую зону
  записи. Доменные факты агент перечитывает из feature-артефактов.
- `status.md`, `docs/backlog.md` и корневые файлы решения (`*.sln`,
  `Directory.*.props`, lock-файлы пакетов и т.п.) меняет только оркестратор;
  остальные агенты возвращают запрос на изменение этих файлов.
- При параллельной работе соблюдай зоны владения из
  `docs/conventions/git.md`. Не используй `git add -A` или `git add .`.
- Каталог legacy-системы (если объявлен в `AGENTS.md`) всегда read-only.

## Гейты и циклы дефектов

На каждом применимом gate покажи человеку краткое summary, diff/артефакт и
открытые вопросы. Продолжай только после явного approve/reject. Значение
`gate-N` выставляет человек; агент может лишь записать полученный в чате
вердикт с датой.

QA/review возвращают дефекты разработчику максимум два раза. После второй
неуспешной итерации остановись и эскалируй человеку: перечисли оставшиеся
дефекты, уже проверенные варианты и блокирующее решение.

## Завершение

После зелёных проверок и code review остановись на `gate-3`. После
`gate-3: approved` выполни раздел «Запрос на merge» из
`stages/06-review-complete.md` и остановись. Merge в `main`, удаление ветки и
финальный `Complete` выполняются только после подтверждения человека.
