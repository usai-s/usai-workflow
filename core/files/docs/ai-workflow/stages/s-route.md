# S-маршрут — bugfix / tech / мелочь (≤ ~2 ч, 1–5 файлов)

**Роли:** backend-developer или frontend-developer → qa-engineer → code-reviewer
**Модели:** dev/QA — standard, review — deep

Сокращённый маршрут из [routing.md](../routing.md): этапы 0–3 пропускаются,
из трёх human-гейтов остаётся один — финальный.

## Процесс

1. **Старт (оркестратор).** Папка задачи создаётся как обычно:
   `docs/features/<id>/status.md` (type: bugfix|hotfix|tech, size: S,
   branch: `<префикс>/<NNN>-<slug>` — `bug/014-quota-rounding`). Для `hotfix`
   ветка берётся от свежего `main`, а не от текущей рабочей. В `status.md`:
   - `stage: 04-backend` или `05-frontend` (с чего начинается работа);
   - `gates: gate-3` — спеки и дизайна нет, значит у первых двух гейтов нет
     предмета; в разделе `## Gates` остаётся только `gate-3: pending`;
   - раздел `## Plan` — 3–5 строк: что чиним/меняем, где, как проверяем.
   Спека и дизайн не пишутся. Для bugfix первая строка плана — шаги
   воспроизведения бага.
2. **Разработка.** По конвенциям (`docs/conventions/*`). Тест, воспроизводящий
   баг / фиксирующий новое поведение, — вместе с кодом; для bugfix тест
   обязан падать до фикса. `api-contract.md` нужен только если задача меняет
   контракт API — тогда правило пометки в `status.md` действует как обычно.
3. **QA (отдельная сессия, чистый контекст).** Облегчённо: полный тест-план не
   пишется. QA-агент проверяет, что план из `status.md` покрыт тестами,
   прогоняет тесты затронутого модуля + smoke соседних, ищет регрессии вокруг
   изменения. Дефекты — списком в `status.md` (Notes), цикл до нуля блокеров.
   Уровень модели — `standard`; действуют правила «Экономии прогонов» из
   [04-backend.md](04-backend.md). Объём проверки задаёт не размер задачи, а
   то, что изменено: прогоняй `scripts/verify.sh` (набор проверок проекта —
   `scripts/verify.config.sh`) и тесты затронутого модуля. Задача, не трогающая код,
   не поднимает тестовое окружение; правка файла зависимостей решения
   (например `Directory.Packages.props` или lock-файла пакетов) поднимает —
   это граф зависимостей, а не «просто конфиг». Вычитка оркестратором
   больше не считается проверкой: у неё нет ни команды, ни кода возврата.
4. **Code review (этап 8).** Как в
   [06-review-complete.md](06-review-complete.md), без изменений — размер
   задачи не повод для слабого ревью.
5. **Human Gate 3 → PR & Complete.** Как в этапах 9–10. Человеку в summary —
   план, что изменилось, как проверить руками.

## Definition of Done

- [ ] `## Plan` в status.md заполнен до начала кода
- [ ] Для bugfix: есть тест, падавший до фикса
- [ ] `scripts/verify.sh` зелёный; команда и код возврата записаны в `## Log`
- [ ] Ревью пройдено, `gate-3: approved`
- [ ] Для hotfix, попавшего в «Пороги `L`» routing.md (необратимая миграция,
      внешний контрагент, auth/секреты): в очереди backlog есть tech-задача
      полного маршрута на то же место — без неё hotfix не мержится

## Облегчённый цикл (docs-only при standing approval)

Если действуют оба условия — (1) задача меняет только `docs/`, `.claude/`,
`scripts/` или хуки, runtime-код не затронут; (2) человек выдал standing
approval на этот класс работ (`AGENTS.md`, «Standing approval») — то
отдельные QA- и review-сессии не поднимаются:

- проверка — `scripts/verify.sh` (команда и код возврата в `## Log`);
- ревью — человек видит полный diff в отчёте о merge;
- остальное без изменений: папка задачи, ветка, worktree, запись плана до
  правок, squash-merge.

Появился хоть один затронутый runtime-файл — цикл обычный, S без скидок.
Правило выстрадано практикой: для правок процессных файлов полный цикл
дублирует verify и diff-ревью человека, не находя ничего сверх них.
