# Этап 2 — Ревью требований → Human Gate 1

**Роль:** requirements-reviewer (чистый контекст, не автор спеки!) · **Уровень модели:** deep
**Вход:** `docs/features/<id>/spec.md`, `docs/legacy/<модуль>.md`
**Выход:** замечания в `spec.md` (раздел «Ревью»), вердикт в `status.md`

## Цель

Найти дыры в спецификации до того, как они станут кодом. Ревьюер настроен
адверсариально: его работа — сломать спеку, а не похвалить.

## Чек-лист ревью

1. **Полнота против legacy:** каждое бизнес-правило из legacy-анализа либо
   покрыто story, либо явно в out of scope, либо помечено `[ИЗМЕНЕНИЕ vs legacy]`.
   Построить таблицу соответствия правило → story.
2. **Проверяемость:** каждый критерий можно превратить в тест. Нашёл
   непроверяемый — переписать конкретнее и пометить как замечание.
3. **Edge cases:** пустые списки, конкурентный доступ, права на каждый шаг BPMN,
   отказ интеграции посреди процесса, повторная отправка.
4. **Противоречия** между stories и с уже принятыми спеками других фич.
5. **Размер:** задачи в бэклоге реально ≤ M.

## Вердикт

- `approved-by-ai` — замечаний нет или все исправлены (мелкие правки ревьюер
  вносит сам, крупные возвращает business-analyst'у, максимум 2 итерации);
- `needs-human-decision` — есть вопросы, которые может решить только человек.

## Human Gate 1

После вердикта оркестратор пишет человеку summary: 5–10 строк — что делает
фича, ключевые решения, список открытых вопросов. Человек в `status.md`:

```
gate-1: approved | rejected: <причина / ответы на вопросы>
```

Дальше этап 3 — только после `gate-1: approved`.
