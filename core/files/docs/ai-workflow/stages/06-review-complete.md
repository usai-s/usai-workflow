# Этапы 8–10 — Code review → Human Gate 3 → PR & Complete

**Роли:** code-reviewer (deep, чистый контекст) → человек → orchestrator (fast)

## 8. AI code review

Ревьюер — отдельная сессия, не участвовавшая в разработке. Смотрит полный
diff ветки фичи против main + `spec.md`, `design.md`, `api-contract.md`.

Порядок проверки (по убыванию важности):

1. **Соответствие спеке** — реализовано то, что написано; ничего лишнего.
2. **Корректность** — ошибки логики, гонки, транзакции, обработка отказов
   интеграций, null/пустые коллекции.
3. **Безопасность** — авторизация на каждом endpoint'е, IDOR (чужие данные по
   id), инъекции, секреты в коде, валидация входа.
4. **Архитектура** — соответствие `docs/conventions/*` и принятым ADR
   (`docs/adr/`): границы слоёв, структура slice'ов, зависимости в правильную
   сторону. Решение, тянущее на ADR, но принятое молча в коде, — замечание.
5. **Тесты** — не только «есть», но и «проверяют то, что заявляют».

Каждое замечание: файл:строка, суть, severity (blocker / major / minor),
предлагаемое исправление. Blocker/major → возврат разработчику (исправления
через этап 4/6, повторный прогон QA по затронутому). Максимум 2 круга; если
не сходится — эскалация человеку.

**Для L-фич дополнительно** — отдельный security-проход: ещё одна сессия
code-reviewer (чистый контекст), которая смотрит ТОЛЬКО безопасность по
чек-листу: авторизация каждого endpoint'а, IDOR (доступ к чужим данным по
id), персональные данные (идентификаторы личности и др.) в логах и ответах API, аудит-трейл
значимых действий, инъекции, секреты в коде. Общий ревьюер, у которого
безопасность — пункт 3 из 5, ей стабильно жертвует.

## Human Gate 3 — ревью юзером

Оркестратор готовит для человека:

- summary фичи: что сделано, отклонения от спеки (если были), решённые
  замечания ревью;
- инструкцию запуска для ручной проверки (docker compose / команды);
- список: что именно посмотреть руками (из acceptance criteria).

Человек в `status.md`: `gate-3: approved | rejected: <замечания>`.

## 9–10. PR & Complete

После `gate-3: approved`:

1. Rebase на main, финальный прогон всех тестов и линтеров. Если main
   принёс свои миграции БД — миграции фичи перегенерируются поверх свежего
   main (конфликт снапшота модели — штатный сценарий этого шага, не сюрприз).
2. PR: заголовок `feat|fix(<scope>): <суть> (<короткий id>)` — например
   `feat(quota): calculate remaining quota balance (feat-001)`; заголовок
   английский, как любой коммит (его же получит squash-коммит); описание — ссылка на
   `docs/features/<id>/`, summary, чек-лист гейтов. PR не открывается и не
   мержится с красным CI (с момента появления CI в project-bootstrap).
3. Merge — **squash**, заголовок squash-коммита = заголовок PR. Полные
   правила ветвления, коммитов и релизов — [../../conventions/git.md](../../conventions/git.md).
   **Мержит человек, не агент.**
4. **Complete входит в сам squash, а не догоняет его.** Перед merge, уже
   после `gate-3: approved`, в ветке задачи проставляется
   `stage: complete` — и это состояние приезжает в `main` вместе со всем
   остальным одним squash-коммитом. Отдельный коммит «mark complete after
   merge» в `main` не делается: `pre-commit` пускает в `main` только
   слияния, и такие коммиты либо пробивали хук обходом, либо требовали бы
   исключения для него — оба варианта хуже, чем строка `stage: complete`,
   записанная на минуту раньше фактического merge. В `docs/backlog.md` при
   завершении ничего не меняется — строка задачи ушла оттуда при старте;
   найденные по ходу задачи и долги — строками в backlog, это единственная
   его правка на этом шаге. Такая строка пишется с литералом
   `NNN` вместо цифр: номер присваивается при заведении ветки, иначе он
   «висит» в незамерженной ветке невидимым для других сессий
   ([../../features/README.md](../../features/README.md)).

## Запрос на merge

Пока у репозитория нет remote, роль PR играет запрос в чат. Агент отправляет
его после `gate-3: approved` и **останавливается**: не мержит, не удаляет
ветку, не проставляет `complete`.

Без такого запроса состояние `main` перестаёт быть очевидным: по нескольким
параллельным веткам на глаз не понять, что уже влито, а что нет.

Формат — коротко, но со всеми пятью блоками:

```
ЗАПРОС НА MERGE · <id>

Ветка:   <ветка> → main
База:    ветвилась от <main | ветка задачи X>
Коммиты: N сверх main — из них моих M, чужих K
         <короткий список: хеш + заголовок>

Изменения: <файлов>, <+строк/-строк>; ключевое одним абзацем

Тесты:   <команда> — <результат>
         не запускалось: <что и почему — Docker, сеть, отсутствие окружения>

Гейты:   gate-1 <вердикт> · gate-2 <вердикт> · gate-3 <вердикт>

Слить:   git switch main && git merge --squash <ветка>
         git commit -m "<заголовок PR>"
         git branch -d <ветка> && git worktree remove <путь>

Жду подтверждения.
```

Готово несколько задач — отправляй **сводный запрос**: одна таблица
(ветка · diff-стат · тесты · пересекаются ли изменённые файлы с соседними
ветками из списка), общие блоки не дублировать. Человек отвечает одним
сообщением («мерджь 1 и 3»); мержатся ветки по одной, после каждой —
проверка, что следующая не конфликтует с обновлённым `main`.

Правила заполнения:

- **Чужие коммиты считать отдельно.** Ветка, отведённая не от `main`, тянет
  за собой чужую работу — squash утащит её в `main` целиком. Если K > 0,
  сначала rebase на `main`, и только потом запрос.
- Пропущенные тесты называть явно. «Не запускалось из-за Docker» — честный
  результат; тот же прогон, поданный как зелёный, — повод не доверять всему
  отчёту.
- Ничего не додумывать: незакрытый вопрос из ревью попадает в запрос строкой,
  а не замалчивается.
