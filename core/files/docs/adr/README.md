# docs/adr/ — Architecture Decision Records

Журнал архитектурных решений проекта. Один файл — одно решение:
`NNNN-<kebab-slug>.md` (номер сквозной: `0001-...`, `0002-...`), шаблон —
`docs/templates/adr.md`. Язык — русский, как у всех артефактов.

## Когда писать ADR

Обязательно, если решение:

- выбирает технологию/библиотеку с долгосрочными последствиями
  (аутентификация, шина сообщений, генерация клиентов API и т.п.);
- задаёт паттерн, который будут повторять все слайсы (обработка ошибок,
  аудит, мультиязычность, versioning API);
- отступает от `docs/conventions/*` — конвенция при этом обновляется
  ссылкой на ADR;
- определяет способ интеграции с внешней системой (платёжный шлюз, госсервис, партнёрское API);
- необратимо или дорого меняется (схема данных ядра, формат идентификаторов).

Не нужен для: локальных решений внутри одного слайса, выбора имён,
всего, что уже зафиксировано конвенциями.

## Процесс

1. ADR пишет тот, кто принимает решение по ходу этапа (обычно backend/
   frontend-developer на этапе плана или оркестратор). Уровень модели — deep:
   это «архитектурные решения» из model routing.
2. Новый ADR создаётся в статусе `proposed` и показывается человеку на
   ближайшем human gate (или сразу, если решение блокирует работу).
   `accepted` ставит только человек — как с гейтами: либо правит сам, либо
   явно подтверждает в чате, и агент записывает это с пометкой.
3. Принятый ADR не редактируется содержательно. Решение изменилось — новый
   ADR, старому ставится `superseded by ADR-NNNN` со ссылкой.
4. Ссылки на ADR из кода/доков — по номеру: `ADR-0001`. В `plan-*.md` и
   `design.md` фичи перечисляются ADR, на которые опирается реализация.
