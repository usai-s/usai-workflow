## Как здесь работают агенты

Вся работа идёт по пайплайну, описанному в **`docs/ai-workflow/README.md`** —
прочитай его перед первой задачей. Кратко:

1. Любая задача сначала классифицируется (тип + размер F/S/M/L) по
   `docs/ai-workflow/routing.md` — от этого зависит маршрут.
2. Каждая фича живёт в `docs/features/<id>/` — там spec, design, api-contract,
   qa-отчёты и `status.md` (текущий этап и вердикты гейтов).
3. Этапы выполняются по инструкциям из `docs/ai-workflow/stages/*.md`.
   Состояние передаётся через файлы, а не через контекст чата — начиная
   работу, прочитай `status.md` фичи и артефакты предыдущих этапов.
4. **Human gates:** после ревью требований, после дизайна и перед PR работа
   останавливается до явного approve человека в `status.md`. Не проскакивай их.
5. Ревью и QA всегда выполняются в отдельной сессии с чистым контекстом,
   не автором артефакта.

## Жёсткие правила

- Не коммитить в main — только ветки задач `<префикс>/<NNN>-<slug>`
  (`feat/001-user-profile-form`); merge — squash-PR после `gate-3`. Ветки,
  коммиты, PR, релизы → `docs/conventions/git.md`; формат id →
  `docs/features/README.md`.
- Не менять `api-contract.md` фичи без пометки в её `status.md`.
- Не редактировать файлы в каталоге legacy-системы (если он объявлен выше).
- Тесты пишутся вместе с кодом; PR с падающими тестами не открывается.
- Секреты — только через переменные окружения / secret-хранилища, никогда в
  коде.
- Запустил процесс в фоне — приложение, поиск, что угодно — либо доведи до
  конца и останови сам, либо явно перечисли в ответе: что именно запущено,
  на каком URL/порту (бери порт из вывода запуска, а не по памяти — dev-
  серверы раздают их динамически) и чем остановить. Необъявленный процесс
  переживёт твою сессию и займёт ресурсы следующей.
- Маршрут задачи подтверждает человек. До первой правки покажи классификацию
  (тип, размер, маршрут, гейты) и дождись ответа — всегда, а не только при
  сомнении. Формат — `docs/ai-workflow/routing.md`, раздел «Подтверждение
  маршрута».
- **Standing approval.** Человек может выдать разрешение на серию работ
  («делай и мерджь без подтверждений») — тогда поштучные подтверждения
  маршрута и merge внутри серии не требуются. Разрешение действует только на
  явно названный класс работ, до отзыва или конца сессии; агент фиксирует его
  в `## Log` первой задачи серии и указывает в каждом Complete. Гейты с
  предметом решения (spec, design, финальное ревью кода) standing approval НЕ
  покрывает — он снимает церемонию, а не контроль.
- **Docs-only-S при standing approval** идёт по облегчённому циклу: без
  QA- и review-сессий, проверка — `scripts/verify.sh`, ревью — человек видит
  diff в отчёте о merge. Условия: меняются только `docs/`, `.claude/`,
  `scripts/`, хуки; runtime-код не затронут. Это расширение F-логики на S
  (`docs/ai-workflow/stages/s-route.md`, «Облегчённый цикл»).
- Merge в `main` делает только человек. Агент после `gate-3: approved`
  присылает **запрос на merge** в чат по формату из
  `docs/ai-workflow/stages/06-review-complete.md` и останавливается. Сам не
  мержит, не удаляет ветку и не считает задачу завершённой до подтверждения.
- Не искать по всему диску и по всему домашнему каталогу: не начинай
  `find`/`grep -r`/рекурсивный обход с `/`, `/c`, `C:\`, `/c/Users` или `~` —
  сужай до конкретного поддерева (`find src -name '*.ext'`). В Claude Code
  широкий поиск блокирует PreToolUse-хук; его устройство, границы и известные
  дыры — `.claude/hooks/README.md`. Для инструментов без хуков это просто
  правило.
- Язык артефактов и UI-текстов — `<русский | ...>`; код, идентификаторы,
  коммиты — английский.
